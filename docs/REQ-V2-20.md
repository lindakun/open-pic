# MediaLib V2：商业级前沿时尚图片平台 · 20 项优化需求（修订版）

> **文档状态**：**v3.1（实施中）** — 拍板决策见 §一；S0 与 S1 部分已落地，进度见 §十
> **目标**：把当前局域网媒体库（`MediaLib/1.0`，FastAPI + SQLite + 原生前端）升级为**具备商业图库产品力与前沿时尚视觉语言**的视觉资产平台。
> **范围**：产品体验、视觉设计、检索发现、内容策展与商业化、交付性能、平台运营。**本版不含安全类需求**（鉴权、权限隔离、HTTPS、防攻击等）。

> **与 v1 的关系**：v1（[REQUIREMENTS.md](../REQUIREMENTS.md)）已落地 18 项底座能力。v2 **不重复 v1 已落项**，只做商业级深度补强，每项标注与 v1 的差异。

2026-11-17 确认，以下 5 项为文档后续所有取舍的**前置约束**，不再作为待议事项：

| # | 决策项 | 拍板结果 | 对文档的连锁影响 |
| :--- | :--- | :--- | :--- |
| 1 | 推进节奏 | **先完善文档，不动手实现** | 本文档即为交付物，进入实施前不再改代码 |
| 2 | 前端形态 | **一次性重构到位**（Vite + 组件框架），不做渐进式 ES Module 改造 | A-01/A-02/A-03/A-04/B-10/E-20 的实现方式全部改为组件化；总工作量上调；新增「前端重构专项」为所有前端需求的公共前置 |
| 3 | AI 能力 | **B-07 打标 + B-08 语义搜图均纳入本期**，外部 API 延后配置 | B-08 由 P2 升为 P1；两项均须实现「未配置 Key 时优雅降级」；新增 API 成本与 provider 抽象要求 |

| 5 | 视觉方向 | **浅色编辑纸感（Light Editorial Paper）** 为主视觉 | A-01 基准色板改为暖白纸感；深色降级为可选主题；字体、留白、图片呈现方式随之确定（见 §2.4） |

### 决策 2 的执行口径：「一次性重构到位」

- **技术栈定为 Vite + Vue 3 + TypeScript + Pinia**（选型理由见 §七）。不引入 SSR/Nuxt——站点以内网访问为主，SEO 由 E-19 的服务端模板直出解决。
- **重构与需求合并实施**：20 项需求不再在旧的原生 JS 上做增量，而是新前端从零搭建时直接按需求实现，**避免"先在旧代码上改一遍、再迁一遍"的重复劳动**。
- **旧前端保留一版作为回退**：重构期间旧 `static/` 目录不动，新构建产物落在 `/app/`；切换以服务端开关控制，验收通过后移除旧版。
- **公共前置工作**（约 5d，单列为 S0 阶段）：工程脚手架、路由、状态管理、API 客户端与类型生成、设计 Token 与组件库基座。此项不被计入任何单项需求，避免重复估算。

### 决策 5 的执行口径：「浅色编辑纸感」

三条硬约束（已写入 A-01 验收标准 §4.1）：

1. **底色不是纯白**：主背景取暖白（`#FAF8F5` 附近），卡片区 `#FFFFFF`，形成极轻的纸张分层而非灰白对比。
2. **对比靠排版不靠色块**：标题用高字重 + 大字号建立层级，禁止用色块/边框分割内容区；分隔线仅为 1px 极浅暖灰（`#EDE8E1`）。
3. **图片是唯一的高饱和元素**：UI 自身除强调色外全部为中性暖灰阶，强调色仅用于当前选中态与主操作（建议低饱和赭石/橄榄系，避免与照片色彩打架）。

## 二、产品定位与设计原则

### 2.1 目标形态

参照 Unsplash / Pexels（发现与检索）、Behance / 500px（编辑化叙事）、Cosmos / Are.na（前沿时尚调性）、Frame.io（资产审阅工作流）的交集：

**一个「看起来像时尚杂志、用起来像专业资产库、交付起来像商业图库」的图片站。**

### 2.2 五条设计原则（裁决后续所有取舍）

| 原则 | 含义 | 当前反例 |
| :--- | :--- | :--- |
| **P1 视觉优先** | 图片即界面，UI 退居背景；排版承担叙事 | 顶栏 9 个等权重按钮，后台管理观感 |
| **P2 零抖动** | 任何异步内容都不改变已渲染元素的位置 | 无 BlurHash 占位，图片解码前为纯色块 |
| **P3 即时反馈** | 交互 < 100ms 有响应，重活走队列且进度可见 | 上传时同步生成缩略图，大图上传期间请求被占住 |
| **P4 可发现** | 任何筛选与资产都能被 URL 表达、分享、被搜索引擎理解 | 筛选状态仅存内存；分享页只有 hash id |
| **P5 可度量** | 每个商业目标都有埋点与指标闭环 | 仅 `views`/`downloads` 两个计数器 |

### 2.3 「纯图规范」（审核补充的关键约束）

商业时尚图站与后台管理系统的分野，在于**界面为图片让路**：

- 默认态**无侧栏、无底栏**，顶栏在滚动 200px 后自动隐藏，向上滚动或鼠标移至顶部 40px 内再出现。
- 卡片默认**无边框、无阴影**，仅在 hover 时浮起 2px 并显信息层（标题 / 尺寸 / 作者）。
- 信息密度靠**排版层级与留白**建立，不靠分割线与背景块。
- 数字（尺寸、体积、色值）统一用等宽字体，建立「专业工具」质感。

### 2.4 主视觉方向：浅色编辑纸感（已拍板）

**定调**：整体观感参照独立杂志的纸张质感与编辑部排版，而非深色影院或 SaaS 后台。浅色是**主意视觉**，深色保留为可选主题（`prefers-color-scheme` 与手动切换），但深色不作为设计基准——所有 Token 与对比度校验以浅色为准，深色做等价映射。

**基准色板（暖纸系，非纯白）**：

| Token | 值 | 用途 |
| :--- | :--- | :--- |
| `--paper` | `#FAF8F5` | 页面主背景（暖白，模拟纸张） |
| `--surface` | `#FFFFFF` | 卡片、弹层（与底色形成极轻分层） |
| `--ink` | `#1A1815` | 主文字（暖黑，非纯黑） |
| `--ink-muted` | `#6F6A63` | 次要文字 |
| `--rule` | `#EDE8E1` | 1px 分隔线（极浅暖灰） |
| `--accent` | `#8C6A4A` | 强调色（低饱和赭石，不与照片争色） |
| `--accent-soft` | `#F0E7DC` | 选中态浅底 |

**四条硬约束**：

1. **底色不纯白**：主背景取暖白，卡片纯白，靠极轻明度差分层，不用灰底白卡。
2. **对比靠排版不靠色块**：标题用高字重 + 大字号建立层级；禁止用色块或粗边框分割内容区；分隔线仅 1px 浅暖灰。
3. **图片是唯一的高饱和元素**：UI 自身除强调色外全部中性暖灰阶；强调色只用于当前选中态与主操作。
4. **留白即叙事**：区块间距使用 8px 基准的大尺度（48/64/96px）而非 16/24px，让版面"呼吸"，这是编辑纸感与后台管理观感的根本差异。

### 模块 A：视觉语言与浏览体验（5 项 · 30d）

#### A-01 设计系统与「浅色编辑纸感」视觉基座 `[P0]` `6d`

> 工作量由 4d 上调至 6d：主要增量是「浅色纸感」的完整色阶体系 + 组件库基座（组件化重构后不再写裸 CSS）。

- **现状**：`app.css:1` 仅 12 个 CSS 变量，正文 13.5px 系统字体栈；深浅主题靠 `html[data-theme]` 切换；顶栏 9 个按钮等权重，整体是深色后台观感。
- **需求**：
  - **三层 Token**：`primitive`（暖纸色阶 50–950、间距、层级）→ `semantic`（paper/surface/ink/rule/accent）→ `component`。组件层禁止硬编码颜色。基准色板见 §2.4。
  - **浅色为主、深色等价映射**：默认跟随 `prefers-color-scheme`，可手动切换并持久化；两套主题由同一组 semantic token 派生，深色仅替换 primitive 层。

- **验收**：

### 模块 D：性能与可靠性（3 项 · 10d）

#### D-16 入库与导出管线异步化、任务可靠性 `[P0]` `3d`

- **现状（审核指出的真实阻塞点）**：`server.py:218` 上传时**同步**执行 `make_thumbnails`，视频还要转码，期间请求被占住；`TaskManager` 重启后库内 `pending/running` 任务无人接管；物理删除（`_physical_remove_items`）不清理新增缓存产物。
- **需求**：
  - 上传接口只做落盘 + 建记录，立即返回 `id` 与占位态；**`extract_metadata`（ffprobe/Pillow）与 `make_thumbnails` 同样下沉队列**——当前 `server.py:217-218` 两者都是同步执行，是上传慢的主因。前端卡片显示「处理中」骨架直到完成。
  - **近重复检测（`db.py:566` `find_near_duplicate` 全表拉 phash 逐行比对）移出请求路径**：改为入库后异步比对，或按 `phash` 前 2 字节建前缀索引分桶后再算汉明距离，避免逐行扫。命中只作提示，不阻塞入库。
  - `TaskManager` 启动时扫描 `pending/running`：`running` 重置为 `pending`，带最大重试次数与退避。
  - 删除资产时级联清理：缩略图、预览、播放副本、`/img` 变换缓存、BlurHash 记录、向量与 FTS 行。
  - 色彩分桶与拼音列在入库时预计算（供 B-06 / B-10 使用）。
- **验收**：
  1. 上传 50MB 视频接口返回 < 1s（**含 ffprobe 元数据提取已下沉**），缩略图在后台完成且 SSE 有事件。
  2. 处理中强制 kill 进程并重启，任务自动恢复并最终完成（无永久 `running` 悬挂）。
  3. 删除资产后，其 `/img` 缓存、缩略图、FTS 行、向量全部消失（脚本断言文件与表计数）。
  4. 上传期间并发 `/api/items` P95 劣化 < 30%。
  5. 近重复检测在 1 万资产下 P95 < 50ms，且不阻塞上传响应（`EXPLAIN QUERY PLAN` 无全表扫）。

#### D-17 万级资产虚拟滚动与位置恢复 `[P1]` `3d`

- **现状**：`app.js:142` 已是绝对定位列式瀑布流（v1 REQ-03 已落地，无重写必要）；但 DOM 随滚动无限增长，无回收，无位置恢复。
- **需求**（降级为 P1，只补虚拟化）：
  - 视口外节点回收：保留可视区 ± 2 屏 DOM，其余替换为等高占位，滚动条总高按累计高度真实还原。
  - 回收时以 `{itemId, top, height}` 快照驱动占位，保证滚动条总高不变。
  - **位置恢复按锚点而非像素**：记录「首个可视卡片 id + 其内偏移比例」，列数变化后仍能定位到同一资产（纯像素恢复在列数变化时会偏离原锚点）。
  - 滚动位置存 `history.state`（不进 URL），返回列表时还原。
  - 弱网（`navigator.connection.saveData`）批量降为 24。
- **验收**：
  1. 加载 2000 条后 DOM 节点数稳定 < 200。
  2. 连续滚动 100 屏，滚动期间 Long Task（>50ms）数量为 0。
  3. 返回列表后首个可视卡片是同一 `itemId`；并在窗口宽度从 1440 改到 768（列数 5→3）后重试，仍定位到同一资产。
  4. 回收/复现过程中已有卡片零位移（`getBoundingClientRect` 采样断言）。

#### D-18 性能预算与运营度量（合并原 16+19）`[P1]` `4d`

- **现状**：无任何前端埋点；`/api/analytics` 仅库内统计，无时间维度与漏斗；`views`/`downloads` 为整数计数器，无事件级数据。
- **需求**：
  - **性能侧**：接入 `web-vitals` 采集 LCP/INP/CLS/TTFB，按页面类型上报 `/api/metrics`（**默认关闭，环境变量开启**）；预算：首页 LCP ≤ 2.0s、INP ≤ 200ms、CLS ≤ 0.02、JS 首包 gzip ≤ 120KB；**不建分位数看板**（内网单用户样本无意义），改为 CLI 报告脚本 `scripts/perf_report.py` 直接输出 P50/P75/P95；本地跑 Lighthouse，超预算退出码非 0。
  - **运营侧**：`events(id, item_id, type, ts, page, referrer, device, meta)`，类型含 `impression/view/download/like/collect/search/share`；曝光用 IntersectionObserver（停留 ≥1s 才计），10s 或 20 条批量上报；看板含 7/30 日趋势、Top 资产漏斗、**零结果搜索词榜**、设备与来源分布。
  - **写锁竞争**：审核指出 `db.py:153` 全局写锁串行化，高频埋点需合并为批量事务写入。
- **验收**：
  1. 访问 20 个页面后 `metrics` 表可查到对应记录，含页面类型与设备类别。
  2. 任一资产可查 7 日曝光/点击/下载漏斗，且满足曝光 ≥ 点击 ≥ 下载。
  3. 零结果搜索词能在看板筛出。
  4. 单次页面交互产生的埋点请求 ≤ 1（批量合并），埋点失败静默降级。
  5. Lighthouse 首页 LCP > 2.0s 时检查脚本退出码非 0。

## 八、风险与前置依赖

### 8.1 重构专项风险（决策 2 引入）

1. **一次性重构的回归面覆盖不全**：旧前端 849 行 JS 承载了多选、合集、回收站、任务中心、统计面板等十余个交互，重写时易遗漏边缘行为。**缓解**：旧前端保留 `MEDIA_LIB_FRONTEND=legacy` 开关直至 S2 结束；重构前先用 Playwright 对现有 12 条主流程录制基线用例，新前端逐条对齐。

3. **构建步骤引入的部署复杂度**：原先改文件即生效，重构后需 `pnpm build`。**缓解**：构建产物入库并在 CI 产出；NAS 端部署脚本增加 `--build` 参数，失败时自动回退到上一版产物目录。
4. **前端工程量被低估**：Vue 生态成熟但仍需自建组件库（不引第三方 UI 库）。**缓解**：S0 阶段先做 6 个基础组件再开 S1，组件库基座完成度作为 S1 的准入门槛。

### 8.2 环境与数据风险

5. **NAS 算力**：AVIF 编码与批量导出 CPU 压力大，需确认核数与是否允许夜间批处理（影响 A-05、C-13）。
6. **磁盘空间**：变换缓存 + 多格式导出会带来 1.2–1.8 倍存储增长（影响 A-05、C-13）。
7. **数据迁移**：`slug / status / license / blurhash / 色相桶 / 拼音列` 需对存量资产一次性回填，须提供幂等迁移脚本与回滚方案（影响 B-06、C-11、C-12、E-19）。
8. **v1 契约兼容**：`/t/ /f/ /p/` 路径、`/api/stats`、`POST /api/upload`、`server.py` CLI 参数不可破坏（影响 A-05、D-16）。

10. **FFmpeg / exiftool**：EXIF 清洗与水印依赖外部二进制，需确认 NAS 环境版本。
11. **本版不含鉴权**：C-14 选片链接靠 token 访问，安全性明确不在本版范围，后续若开放公网须单独立项。

### 已落地的技术细节

**授权与管线（C-11 / D-16）**：

- 上传接口返回时间从"等 ffprobe + 缩略图"降至 **19ms**（实测），重活全部进队列。
- `synchronous=1` 参数保留同步路径，`ingest.py` 与既有测试不受影响。
- 近重复检测由全表逐行算汉明距离改为 **phash 首字符分桶**，万级库下候选量大幅下降。
- 授权字段只接受白名单列（实测注入 `views` 被忽略），避免任意列写入。
- EXIF 清洗实测：GPS 与机型被剥离、拍摄时间保留、**原图字节不变**。

**无障碍与双语（E-20）**：

- 未引入 vue-i18n（约 20KB），自建轻量实现：扁平字典 + `{name}` 占位符 + 英文单复数（`one | other` 选形）+ 缺失 key 回退。
- `localStorage` 访问全部包 try/catch：隐私模式或测试环境不可用时静默降级，不影响功能。
- axe-core 实测暴露并修复 3 类真实问题（非纸面检查）：
  - `--ink-faint` 对比度仅 1.94–3.18（需 ≥4.5）→ 加深色值至 `#767068`（4.62:1）
  - 卡片信息层用整体 `opacity: 0.62` 弱化，把合规对比度压到 1.94 → 去掉透明度，直接用合规色
  - 语言切换按钮/首页链接的 `aria-label` 未包含可见文字 → 改用 `sr-only` 或修正文案
- 最终三页（首页/浏览/灯箱）axe violations 均为 0。


**检索（B-06）**：

- 根因：`items_fts` 表建了、也写了，但 `query_items` 完全没查它——实际是六路 `LIKE '%kw%'` 全表扫。
- 现在查询走 `MATCH`，`EXPLAIN QUERY PLAN` 确认命中 `SCAN items_fts VIRTUAL TABLE INDEX`，不再扫 `items`。
- 中文分词：jieba 可用时用 `cut_for_search`，缺失时退化 2-gram（当前环境未装 jieba，实际走 2-gram，两字词仍可命中）。
- 单字查询不构造 `MATCH`（会命中近乎全库），改为标题前缀 + 标签前缀匹配。
- 旧库兼容：`_migrate_fts_seg` 检测到 FTS 表缺 `seg` 列时自动重建并回填，实测存量库可直接升级。


- **`/img/{id}?w=&fm=&q=`**：尺寸白名单 360–3840、上限 4096；缓存键含源文件 mtime，源更新自动失效；LRU 上限默认 4GB（`MEDIA_LIB_IMGCACHE_BYTES` 可调）；AVIF 编码失败回退 WebP，彻底失败回退原图，请求不失败。
- **旧路径完全保留**：`/t/ /f/ /p/` 与存量 `_sm/_md/_lg` 未受影响，v1 契约兼容。
- **前端竞态控制**：列表请求带自增序号，过期响应直接丢弃，解决快速切换筛选时的覆盖问题。
- **筛选状态**：全部写入 URL query（`replaceState` 防抖 200ms），滚动位置不进 URL。
- **无障碍**：分面用原生 `<details>`/`<summary>`、卡片用原生 `<button>`、浮层用 `<dialog>`。

### 11.4 部署期间发现并修复的问题

1. **视频卡片纯黑块**（线上验收发现）：`SmartImage` 对视频回退到 `/f/{file}`，浏览器将视频当图片解码失败。改用后端海报帧 `/t/{id}.jpg`，已修复并复验。
2. **部署目录非 git 仓库**：NAS 部署目录原本是纯文件目录。已建立裸仓库 + `git clone` + `rsync` 的正式链路，后续改动一律走 push/pull。
3. **服务重启需提权**：服务以 `picoclaw` 用户运行，`lindakun` 无信号权限。已改用 `sudo` 重启；`ensure.sh` 为幂等脚本，服务已响应时不会重启，因此变更后必须显式停止再拉起。
